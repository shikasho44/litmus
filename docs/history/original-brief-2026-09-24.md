# 「ジェーンドゥの死因」ゲームアプリ 完成版開発設計書

## 1. 開発目的

「ジェーンドゥの死因」をブラウザ上で遊べる完成版ゲームアプリとして開発する。

単なるクイズアプリではなく、プレイヤーが自由な文章で質問し、AIゲームマスターとの会話を通じて事件の真相と死因を推理するゲームとする。

さらに、各事件の背景にある科学・医学・物理・化学・生物などについて、ゲーム終了後に学べる構造を持たせる。

ゲームとして面白いだけでなく、

「遊んだ結果、科学知識が一つ増える」

ことを重要な価値とする。

# 2. 今回の開発範囲

今回は生成AI学習ゲーム等への横展開は考えない。

「ジェーンドゥの死因」を遊ぶための完成したWebアプリの制作に集中する。

将来的な拡張を阻害しない内部設計にはしてよいが、現段階で別シリーズの画面や機能を実装する必要はない。

# 3. コンテンツ利用方針

使用予定：

・「ジェーンドゥの死因」という名称
・基本的なゲームルール

使用しないもの：

・既存キャラクター
・既存イラスト
・既存ストーリー
・既存の問題文章
・既存動画
・既存ロゴ
・その他既存作品固有のクリエイティブ

問題、文章、画像、科学解説等は新規制作する。

正式公開前に権利者へ確認を行う予定。

そのためタイトル部分は設定値として管理し、コードへハードコードしない。

例：

APP_TITLE
GAME_TITLE
COPYRIGHT_NOTICE
OFFICIAL_RELEASE_ENABLED

などを設定から変更できる構造にする。

# 4. 最重要設計思想

問題の真相を生成AIに作らせない。

ゲーム開始前に、問題データとして

・何が起きたのか
・死因
・科学的メカニズム
・登場人物
・時間
・場所
・状況
・重要な事実
・関係のない事実
・質問に対する正答
・プレイヤーへ開示してよい情報
・ゲーム途中では開示してはいけない情報
・正解条件

を確定させて保存する。

生成AIは、

「決められた真相をプレイヤーとの自然な会話を通して運用するゲームマスター」

としてだけ使用する。

# 5. 基本ゲームフロー

## 5-1. Case Start

事件タイトルと導入文章を表示する。

例：

「深夜の研究室で女性が死亡していた。

外傷はなく、争った形跡もない。

部屋の中には壊れた機械が一台だけ残されていた。

彼女はなぜ死んだのだろう？」

この時点では必要最低限の情報だけを提示する。

## 5-2. Investigation

プレイヤーは自由入力で質問する。

例：

「毒物は関係していますか？」

「機械は動いていましたか？」

「死因は窒息ですか？」

「女性に持病はありましたか？」

AIゲームマスターが回答する。

## 5-3. Discover

重要な質問をすると、新しい事実や証拠が発見される。

例：

「重要な情報を発見しました」

・部屋の換気装置は停止していた
・死亡直前まで機械は稼働していた

発見した情報は「捜査ノート」へ保存する。

## 5-4. Deduction

プレイヤーが十分だと思った時点で、

「死因を推理する」

を選択する。

自由文章で、

・何が起きたのか
・何が死因なのか
・その理由

を回答する。

## 5-5. Judgment

AIとルールベース判定により、

・正解
・ほぼ正解
・重要な要素が不足
・推理を続ける必要がある

を判定する。

## 5-6. Solution

正解後、

・事件の真相
・死因
・伏線
・質問から得られた情報
・科学的な仕組み

をまとめて表示する。

## 5-7. Science

最後に科学解説パートへ進む。

この部分をゲームの重要機能として実装する。

# 6. ゲーム中の基本回答

基本回答は、

「はい」
「いいえ」
「関係ありません」
「一部関係があります」
「その質問には今は答えられません」
「質問をもう少し具体的にしてください」

を中心とする。

必要な場合のみ短い補足を加える。

回答を長文にしすぎない。

ゲームマスターが解説を始めたり、プレイヤーが聞いていない情報まで説明したりしない。

# 8. FACTの重要度

# 9. spoiler_level

ゲーム中に核心を漏らさないため、別途spoiler_levelを持つ。

例：

2

3

4

# 12. Question Processor

入力された文章を正規化する。

処理例：

誤字

を整理する。

ただし意味を書き換えない。

# 13. FACT Retrieval

全FACTを毎回LLMへ渡さない。

プレイヤー質問から関連しそうなFACTを抽出する。

候補：

・キーワード検索
・全文検索
・Embedding検索
・ハイブリッド検索

上位5〜15件程度を候補として取り出す。

# 14. Jev Pre-Judge

Jevには文章を書かせない。

Jevの判断結果は直接プレイヤーへ表示しない。

ゲーム内部の制御だけに使用する。

# 15. Jevの役割

Jevに担当させる候補は以下。

・質問分類
・関連FACT選択
・Yes / No判定
・質問の重要度判定
・ネタバレ危険度
・情報開示可否
・プレイヤーが核心へ近づいているか
・回答内容がFACTと矛盾していないか
・LLM回答が余計な情報を漏らしていないか
・最終回答が正解条件を満たしているか

# 16. LLMの役割

LLMは主に文章表現を担当する。

Jevまたはコードによって、

「何を答えてよいか」

を決定したあと、

「どう自然に答えるか」

をLLMへ任せる。

つまり、

Jev
判断

LLM
表現

コード
ルール

という役割分担にする。

# 17. 高速回答ルート

すべての質問でLLMを使用しなくてもよい。

Jevのconfidenceが高く、

ANSWER_CLASSが明確で、

追加説明が不要な場合、

コードから直接

「はい。」

「いいえ。」

「関係ありません。」

を返す。

これをFAST PATHとする。

通常ルート：

質問
→ Jev
→ LLM
→ Jev
→ 回答

高速ルート：

質問
→ Jev
→ 定型回答

これによって、

・レスポンス速度
・API料金
・回答ブレ

を減らせる可能性がある。

# 18. LLM Post-Check

LLMが作った文章をそのまま表示しない。

Jevによる最終チェックを入れる。

確認項目：

FACTに存在しない内容を言っていないか

真相と矛盾していないか

プレイヤーが聞いていない情報を漏らしていないか

spoiler_levelを超えていないか

答えそのものを先に言っていないか

回答形式として適切か

PASSなら表示。

FAILなら、

1回だけLLMへ修正させる。

それでもFAILの場合、

安全な定型回答へフォールバックする。

# 19. ハルシネーション対策

目標は、

「LLMに正しい答えを考えさせる」

ことではなく、

「正解データから許可された情報だけを自然文へ変換させる」

こと。

以下を徹底する。

・真相はDB側に固定
・FACT外の情報生成禁止
・関連FACTだけLLMへ渡す
・FACT IDを内部的に保持
・回答後に検証
・不明な場合は不明と回答
・推測禁止
・矛盾検出
・ログ保存
・自動テスト

# 24. Science Learning System

「死因を当てて終わり」

にはしない。

# 25. ゲーム中の科学情報

など。

# 47. 完成条件

次の条件を満たした場合のみ「完成」とする。

プレイヤーが説明なしでもゲーム開始できる。

自由な日本語質問に対応できる。

設定外の事実をAIが作らない。

同じ質問に大きく矛盾する回答をしない。

核心を勝手に漏らさない。

最終推理を意味的に評価できる。

科学解説まで完結する。

途中保存できる。

スマートフォンで快適に遊べる。

Caseを管理画面から追加できる。

Case追加時にコード修正が不要。

AIの精度を自動評価できる。

Jevあり・なしを比較できる。

AI処理時間を計測できる。

API費用を計測できる。

エラーから復帰できる。

公開運用可能な状態になっている。

# 49. AIエージェントへの実装指示

この設計書を仕様の基準として実装すること。

単なるモック画面やデモで終了しない。

最終的に一般公開できるWebアプリとして完成させる。

不明点があっても開発を停止せず、
合理的な仮定で進行し、
仮定した内容をdocs/decisions.mdへ記録する。

ゲームロジックとコンテンツを分離する。

Caseデータを変更するだけで新しい事件を追加できる設計にする。

生成AIへゲームの真相を作らせない。

DBに存在しない事実を生成させない。

AI出力は必ず検証可能にする。

Jevについては導入効果を測定できる構造を最初から実装する。

各Phase終了時にREADMEまたは開発ドキュメントへ、

実装済み機能

テスト結果

未解決事項

既知の問題

次工程

を記録する。

最終的に、

「AIが会話するゲーム」

ではなく、

「固定された正確な世界を、AIを使って自由に探索できる推理ゲーム」

を完成させること。
